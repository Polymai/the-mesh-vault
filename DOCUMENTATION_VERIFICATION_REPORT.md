The protocol description is based on the current code rather than the former recovery-envelope design. The protocol-v3 Supabase artifacts have now provisioned successfully. That confirms deployment acceptance of the artifacts, not the still-unrun live upload, recovery, TURN or physical-phone journeys.

## Documentation inventory result

- `js/content/public-documents.js`, `ai-manifest.json`, the defensive publication, release/UAT reports and test plan now identify the active contract as protocol v3.
- `DOCUMENTATION_INDEX.md` separates current sources of truth from contributor instructions and historical records.
- The initial Polymai task/mirror, resolved provisioning incident and chronological changelog remain available for traceability but are explicitly labelled as superseded where they describe pre-v3 behavior.
- No current public document describes hosted recovery envelopes, wrapped segment keys, pre-v3 restore compatibility or uninterrupted mobile-background execution as implemented behavior.

## Security statements that must remain qualified

- “Keys never leave the device” applies to the Mesh Key root and owner private signing material during ordinary vault operation. A user who deliberately creates a share link exports a limited capability containing segment access grants.
- The root seed is stored in the origin's private IndexedDB so the vault can reopen. A compromised browser profile, device or same-origin script can therefore compromise it.
- Anonymous Supabase Auth is pseudonymous, not invisible: Supabase and network providers can process IP addresses and technical request metadata.
- Signed and hashed cache records provide integrity checks; permissive anonymous cache writes can still create availability or abuse risk.
- A Mesh Key provides authority and deterministic key derivation. File recovery also requires enough valid, reachable shards.
- PWA installation, Wake Lock, notifications and Anchors do not guarantee that a mobile operating system will keep a browser process alive.
- The optional Android foreground service is more durable than a PWA but remains subject to force-stop, Doze, network loss and OEM battery policy. Its native worker receives public node configuration and opaque storage/control objects, never the Mesh Key or root-derived file keys.

## Removed obsolete claims

The current release documentation must not describe any of these as protocol-v3 behavior:

- recovery envelopes in Supabase or on Anchors;
- wrapped per-segment decryption keys in manifests or coordination storage;
- protocol-v1/v2, ECDSA P-256 or six-group legacy recovery compatibility;
- a complete cold-start recovery proof for the new v3 format;
- provisioning success as proof that live peer transfer, recovery, deletion or mobile continuity has passed.

## Verification still required

1. Inspect the provisioned schema to confirm the one-time `local-root-key-v3` reset completed and no legacy recovery/key-envelope tables or columns remain.
2. Repeat creation, reload and Mesh-Key portability checks against the deployed origin in Chromium, Firefox and WebKit.
3. Run the uploader-offline golden recovery with a fresh v3 vault and compare the final SHA-256 byte for byte.
4. Repeat real multi-device WebRTC, TURN-only, mobile suspension, shard repair and deletion tests.
5. Build the generated APK/AAB and execute the Android screen-off, reboot, stop, force-stop, native storage and hosted-data inspection matrix in `ANDROID_BACKGROUND_NODE.md`.

Until those gates pass, protocol v3 is a **provisioned pre-release candidate**, not a production-verified release.
